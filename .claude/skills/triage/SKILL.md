# triage

人間はコードを読まないので、不具合の受け入れ条件は「再現テストが通ること」にする。
この手順の成果物は、再現テストのコードを本文に含んだ `ready` な Issue。コードは push しない (修正 PR がテストごと入れる)。

```sh
R="repos/$(git remote get-url origin | sed -E 's#.*github.com[:/]##; s#\.git$##')"
```

## 1. 報告を読む

Issue の本文とコメントを読む。「何をしたら」「何が起きて」「何を期待したか」の 3 つが揃っているか確認する。
揃っていなくても、コードから推測できる範囲はまず自分で埋める。

## 2. 再現する

- 報告の手順をテストの形に落とす。既存のテストの置き方 (`CLAUDE.md` の「テストの置き方」) に従う。
- `make test` で、そのテストが**報告どおりの理由で**失敗することを確認する。別の理由で失敗していたら、テストを直す。
- 原因の見立てがついたら書き留める。直すのはここではない。

## 3. 結果を Issue に反映する

### 再現できたとき

`.github/ISSUE_TEMPLATE/work-item.md` の構成で本文を書き直す (`gh api -X PATCH "$R/issues/$N" -F body=@<本文ファイル>`)。

- 達成したい状態: 期待する振る舞い
- 完了条件: 「以下の再現テストが通る」+ テストコードをそのまま貼る。テストファイルの置き場所も書く
- 参考情報: 原因の見立て、関係するファイル

`ready` を付ける。`bug` は残す。

### 再現できないとき

分かったこと、試したこと、足りない情報を箇条書きでコメントし、`needs-input` を付ける。
質問は人間が答えられる形 (操作、画面、環境) にする。コードの話は聞かない。

## 4. 報告

Issue 番号と結果 (ready / needs-input)、再現テストの場所を 1〜3 行で報告して終える。
対話セッションで「そのまま直して」と言われたら `/work-issue <番号>` へ続ける。
